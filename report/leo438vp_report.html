LEO 438VP control computer: how LEO-32 talks to the ISA image-processor board and the fiber links

A static analysis of the drive image, done without running any code. It traces the path from the LEO-32 user interface down to the bytes on the fiber-optic serial links, lists every command table that survived in the binaries, and proposes a staged plan for replacing the Win98 PC and its custom ISA board.

Update, 15 November 2026. Stage 2 (path A in §12) is done. Every link has since been captured on the scope or with a serial logger and written up as an interface specification: EHT, stage / vacuum, VP, and the four EO fibers. LEO-32's electron-optics model was decompiled, run in an emulator, and fitted to about 130 lens states captured on 15 November (§9). The replacement (path C) is being built: a Teensy 4.0 control box, the Open Beam Interface for imaging, and a browser control page. 1Key findings

The boardA TMS34020 graphics processor is the real controller

The ISA card is the Cambridge/Leica "Stereoscan Image Processor": a TI TMS34020 GSP running the TIGA graphics manager plus LEO's own multitasking kernel and ten loadable modules. The PC never touches the fiber links directly. It sends TIGA function calls to the GSP, and GSP code drives the links.

ISA resourcesI/O 0xA300–A301 page registers + 32 KB memory window at D000:0000

Each GSP address is reached by writing bits 31–18 to two page registers and then doing a 16-bit access in the D0000h window. Probably IRQ 9 for GSP→host interrupts.

Fiber links 1 & 2Two 16550-type UARTs, 9600 baud 8N1, ASCII "dot commands"

UART A (GSP 0x60300000) talks to the EHT/gun supply. UART B (0x60380000) talks to a combined Stage/Vacuum comms CPU. Commands look like .SX, .VL, .B, terminated by CR/LF.

Scan / opticsAn ADSP-21xx DSP programs a remote raster engine

The DSP sends start/step/count/flyback values for X and Y, plus all lens and stig set-points, over a 10-bit remote register bus. X/Y samples are not streamed from the PC (§8). Captured since: the bus is a 3.6864 Mbit/s fiber of 32-bit register frames with a reply fiber; the other two fibers are frame / line gates, not a pixel clock. The X ramp runs from the EO board's own clock.

Electron opticsLEO-32 computes every lens from a column model

Condensers and objective come from kV, WD, probe current, Optibeam mode and aperture (not magnification). The model was decompiled from g200.440, fitted to 130 captured lens states and ported to the new controller: objective within 1.6 DAC counts rms, condensers within a few % (§9).

ReplacementPath C is under way

A Teensy 4.0 control box drives the EHT, stage / vacuum, VP and EO links and enforces the interlocks. The Open Beam Interface does the imaging, and a browser page replaces LEO-32. The PCB is at the fab (§12).

SymbolsThe GSP modules still carry their symbol tables

Every function and global in the ~3 MB of GSP code is named (_InitEHTUART, _send_stage_command, _DSPISR…). This makes full decompilation practical.

HealthThe machine is logging EHT-link timeouts

The live log (to 15 Jul 2026) has 95 "EHT set comms timeout" events, two "Filament Blown" errors and repeated Penning-gauge warnings. The EHT fiber link is the first one to scope.

2System architecture

The PC is a host for one large ISA card. The card owns the video path, the scan generator, and the serial links to the column electronics. The PC's own S3 VGA output goes into the card and comes back out mixed with the live SEM image. Vacuum control in VP mode is the one exception: it runs from the PC's own COM2 to a separate "Orsay" controller board.

3Software stack

LEO-32 is a 32-bit shell (MFC and Visual Basic 6) wrapped around a 16-bit core written for Windows 3.1 between 1994 and 1996. A call from the UI crosses a 32→16-bit flat thunk, passes through one of eight "controller" DLLs, and is turned into a TIGA extended-function call that runs on the GSP.

4PC ↔ board ISA interface

There is no Windows VxD or kernel driver for the board. The hardware is set up from DOS in AUTOEXEC.BAT, before Windows starts, and Windows code then reaches it through the resident TIGA communication driver. The small DOS tools in C:\GSPUTILS (Borland Turbo C, 1993) contain the clearest copy of the raw access routine.

Window addressing

TMS340 processors use bit addresses. The window covers 218 bits (32 KB), so the page registers carry GSP address bits 31–18 and the low bits become the offset inside the window. Recovered from GSPHALT.EXE:

/* write one 16-bit word to GSP bit-address A (reconstructed from GSPHALT.EXE @0x265) */
void gsp_poke16(uint32_t A, uint16_t v) {
    outb(0xA301, (A >> 24) & 0xFF);          /* GSP addr bits 31..24              */
    outb(0xA300, (A >> 16) & 0xFC);          /* bits 23..18 (bits 17,16 ignored)  */
    *(volatile uint16_t far *)MK_FP(0xD000, (A >> 3) & 0x7FFF) = v;
}
/* GSPHALT: poke(0xC0000100, 0xC300) then poll bit 4 of the same register up to 1000 times
   → writes the GSP's own host-control register (HSTCTLH) through the window to halt it. */

Boot sequence (from AUTOEXEC.BAT → LEOEXEC.BAT C:)

  1. MCS2GSP C:\GSPUTILS\MMLCA.MCS: resets the Xilinx LCAs on the memory module, clocks in the Intel-hex bitstream (349 lines), and checks DONE.
  2. GSPHALT: halts the TMS34020 through its host-control register.
  3. EPROM OFF: moves the board's boot EPROM from GSP 0xFFF00000 to 0xEFF00000 so TIGA can own the vector area.
  4. TIGACD: installs the TIGA Communication Driver TSR (reads TIGA.CFG: board "LEO 400 Series 16 Colour Board 1024x768 60Hz").
  5. TIGALNK -lx: loads TIGAGM.OUT (graphics manager + LEO kernel) and starts it. On failure it prints "SEM INITIALIZATION FAILURE".
  6. In Windows, SEM_INIT.EXE (1996) loads TIGAWIN.RLM, downloads DPRAM.IMG to the DSP, replays SEM_INIT.DAT, and turns its "traffic light" green.
  7. leoserv.exe loads M007…M800, and each loads its GSP extension with TIGALNK-style relocation (install_rlm), getting back a module ID.

5Inside the board: GSP address map and runtime

The GSP runs TI's TIGA 2.20 graphics manager, extended with a small preemptive kernel (_Spawn, _Suspend, _Activate, _PutQueue/_GetQueue, _Announce/_Expect). Each module spawns a process (_ProcEHTCmds, _ProcStgVacCmds, _ProcDSPCmds, _EO_Process…) that owns its hardware. Host calls drop commands into that process's queue, and replies come back through response buffers (EhtTigaRsp, StgRspBuff…), which the host polls.

Peripheral addresses below come from 32-bit immediates in the GSP code and are not relocated, so they are fixed hardware addresses. TMS340 addresses are bit addresses; divide by 8 for a byte address.

; _InitEHTUART (g100.440 @0x1EBB0) — register n is at base + 32·n bits
MOVI  0x60300000, A0
MOVB  0x80 → *A0(96)    ; LCR = 0x80   DLAB on
MOVB  0x0C → *A0(0)     ; DLL = 12
MOVB  0x00 → *A0(32)    ; DLM = 0      divisor 12 → 9600 baud at 1.8432 MHz
MOVB  0x03 → *A0(96)    ; LCR = 8N1
MOVB  0x05 → *A0(32)    ; IER = RX data + line status
MOVB  0x08 → *A0(128)   ; MCR = OUT2 (IRQ enable)   [UART B uses 0x0A: OUT2 + RTS]

The baud rate assumes the standard 1.8432 MHz UART crystal. If the board uses a different clock, the divisor of 12 still pins the ratio, so a scope on the fiber receiver will settle it in seconds.

6Command tables (host → GSP)

Every TIGASEM.DLL export is a thin stub that pushes its arguments and issues one TIGA extended call. The command word is the module ID that TIGALNK assigned at load time, ORed with 0x4000 and the function's index in that module's .TIGAEXT table. Two spot checks agree: READDPRAM sends id|0x4006, and entry 6 of g900.rlm is _cp_read_dpram. WRITEEO sends id|0x400B, and entry 11 is _cp_write_eo. The tables below are read from the relocation records of each module, so the index-to-function mapping is exact.

Entries 0 and 1 are usually the module's own init/entry point. These tables are also the natural API surface for a new host driver if the existing board is kept (path B in §12).

8Scan generator path: DSP, raster engine and the four fibers

This section goes deeper than the first pass and now includes the decoded EO register map. The DSP program image (DPRAM.IMG) and the GSP's DSP driver (g900.rlm) were both decoded far enough to follow a scan setting from the user interface down to the registers on the far end of the link. The picture: the PC never streams X/Y samples. The DSP loads start, step, count and flyback values into a hardware raster generator, sets a pixel clock, and then updates registers only per line or per user action.

The DSP is an Analog Devices ADSP-21xx

DPRAM.IMG stores 24-bit words as three bytes plus an FF pad, which is the GSP's 32-bit view of a 24-bit program RAM. The words decode cleanly as ADSP-2100-family code: interrupt vectors every 4 words, RTI=0A001F, RTS=0A000F, DO…UNTIL loops, DIVQ division. The control-register writes match an ADSP-2101/2105-class part: system and wait-state registers at DM 0x3FFE/F, the timer at 0x3FFB–D, SPORT1 at 0x3FF1/2, and internal data RAM at 0x3800. Program words 0x000–0x3F7 are a small resident monitor (command loop and code download). The scan firmware itself lives at PM 0x2000–0x2C99 (about 3,200 instructions).

The remote register bus

Every write the DSP makes to the scan hardware, and every lens or stigmator value the GSP sends, goes through one routine at PM 0x2457:

; DSP PM 0x2457 — write AX0 to remote register (I4 − 0x3400) on target "EO"
AF = 0x0040                    ; target code: 0x40 = EO board  (entry 0x247F uses 0x20 = HRRU)
wait: AR = DM(0x37FF) AND 0x0004; IF NE JUMP wait   ; link busy?
AR = (shadow AND 0xFF9F) OR AF ; DM(0x0040) = AR     ; select target in link-control reg
DM(I4) = AX0                   ; I4 = 0x3400 + register → link sends (address, 16-bit data)
; PM 0x2468 (read): select target, dummy read DM(I4), wait busy, read DM(I4) again → value
  • Address space: 10 bits (0x000–0x3FE) per target, 16-bit data. Targets are selected by bits 5–6 of IP-board register 0x40: 0x40 = EO board, 0x20 = HRRU (the photo recording unit).
  • GSP access: _set_eo_register fills TRANSSTARTADD (0x405/6) with the register number, TRANSNUMBER (0x407/8) with a count, data in the transfer buffer, and TRANSCTRL (0x409) = 0x40, then issues DSP command 0x04. Lens, stigmator and condenser code in g200.440 (_write_EO_value, _gsp_set_C3_current, _gsp_set_condenser_lens_current …) all end up here. So the same link carries both lens/stig set-points and raster-generator settings.
  • Traffic: bursts only. There is one write per register, gated by a busy flag. The DSP writes a handful of registers per scan-rate or format change and a few per line (Y position from the line interrupt). This is the low-bandwidth "EO command" channel you expected.
  • Readback is real. The firmware reads remote registers (0x4B, 0x14, 0x30, board ID 0x90) and waits on the busy flag for the reply. The EO board has one fiber transmitter (HFBR-1521) for this return path; see below.

How a raster is defined (DSP command 0x07)

Scan coordinates are 16-bit offset-binary DAC codes centred on 0x7FFF. The full field is MAXPIXELS × MAXLINES (1024 × 0x303 by default), and a sub-raster (reduced raster, split screen, zoom) is a window inside it. The handler computes:

xstep = 0x7FFF / MAXPIXELS                      ; 31 for 1024 (DIVQ routine at PM 0x2447)
reg 0x40  X start      = 0x7FFF − xstep·MAXPIXELS + 2·xstep·STARTPIXEL   ; 0x03FF for a full raster
reg 0x42  X pixel step = 2·xstep                         ; 62 codes per pixel → 0x03FF … 0xF7FF
reg 0x48  pixels/line  = NUMPIXELS
reg 0x49  blank pixels = BLANKPIXELS, or (0x110|0x120 + k)·f(rate) if 0
reg 0x41  flyback step = 2·(xstep·NUMPIXELS / blank)    ; ramp returns during horizontal blanking

ystep = 0x7FFF / MAXLINES
reg 0x60  Y start  = 0x7FFF − ystep·MAXLINES + 2·ystep·STARTLINE
reg 0x62  Y step   = 2·ystep        reg 0x68 lines = NUMLINES     reg 0x69 = BLANKLINES
reg 0x61  Y flyback step = 2·(ystep·NUMLINES / BLANKLINES)
reg 0x4B  read → write 0 (stop) → reprogram → restore old value (restart)

; spot mode (cmd 0x19) uses the same scale: reg 0x54 = 0x7FFF − xstep·MAXPIXELS + 2·xstep·SPOTX, reg 0x74 likewise for Y

This is a classic digital differential (DDA) raster: each axis has a start code, a per-step increment, a count, and a flyback increment spread over the blanking interval. That pattern only makes sense if an accumulator on the far side adds the step on every pixel clock, with the result driving the scan DACs. Magnification is applied elsewhere, by analogue gain on the scan-coil drivers (mag-range register 0x4D, SCANAMP, FASTLINEAMP/SLOWLINEAMP in DPRAM). Rotation, dual-mag and post-rotation offsets are loaded as coefficient sets into the 0x14/0x15, 0x32/0x33 and 0x71–0x76 registers (commands 0x1A, 0x21, 0x2B).

How the pixel clock is made (DSP command 0x06)

  • SCANRATE (DPRAM 0x40A, 0–15, default 5) is the dwell-time index; M200 exposes 16 rates (DOCOMMANDSCANRATE0…15).
  • For rate ≥ 3 the DSP sets SPORT1 SCLKDIV = 2(rate−3) − 1 with internal SCLK enabled (control 0x6002). The SCLK1 pin then runs at CLKOUT / 2(rate−2), halving at each step. Rates 0–2 use a fixed divider plus a 2-bit local divider in IP-board register 0x58.
  • For rate > 9 the DSP also programs remote register 0x4A = 2(rate−9) − 1 and switches 0x4B from 0x8402 to 0x8422. In other words, a further divider on the far-end board is enabled. A prescaler at the far end only makes sense if that board receives a clock to divide.
  • Rates above DPRAM SLOWLINERATE (6) and DIGILINERATE (8) set mode bits 0x08/0x18 in register 0x4D (slow-line and digital-line modes) and change register 0x4C between 4 and 8.
  • The DSP takes a per-line interrupt (IRQ1 → PM 0x0200) that counts lines, switches between rasters (split/quad/dual-mag), handles end-of-frame, and writes per-line values such as Y position 0x74. The timer interrupt (PM 0x2000) handles slower periodic work (stereo, frame averaging).

The DSP crystal frequency isn't in the software, so absolute dwell times need a scope. The ratios are fixed: each scan-rate step should halve the frequency on the clock fiber.

Captured: there is no clock fiber. The line period is set on the EO board itself (chip 2 register 0x0A = 2n−1 for speed n; line = (r0A+1) × 87.9 µs, 2.81 ms at speed 5). The SPORT1 clock stays inside the IP board.

9Electron optics: how LEO-32 sets the lenses

LEO-32 keeps no tables of lens DAC values. Its GSP module g200.440 holds a paraxial model of the column: gun crossover → C1 → C2 → final aperture → objective → specimen. Every operator control changes one input of the model; the model gives each lens a focal length, and each focal length becomes a coil current for the present kV. The model was decompiled symbol by symbol, run in a TMS34020 emulator around the original g200.440, and compared with lens values captured on the EO fiber. Encoding. Each lens current is a 20-bit code over 3 A, split into a 12-bit coarse DAC (code >> 8) and a fine DAC (low byte, centred on 2048 for the objective). About 130 settled lens states were captured with the beam on while sweeping WD 5–100 mm, probe current 10 pA–100 nA, both Optibeam modes, aperture entry and magnification at 20 kV, plus kV 1–30 kV both ways and a 5 kV block (scope_tools/EO_OPTICS_TEST_PLAN.md, data in analysis/optics/eo_capture_2026-11-15.csv). What they settled:

  • Beam off = 100 V. LEO-32 runs the model on the applied kV, which is 0 with the beam off and is clamped to 100 V. Every earlier lens capture made with the beam off was such a state.
  • Displayed WD is rescaled on the PC side: internal WD ≈ (WD − 1.9 mm) / 1.22. With that, the original code's objective matches the captures within 1–8 counts from 5 to 100 mm and 1 to 30 kV.
  • LEO-32 used its LaB6 gun table and effective condenser calibrations of ≈ 0.94 / 0.90 on this tungsten machine. The likely cause is a filament-type index that differs between the PC and the GSP.
  • Modes: Normal = GSP mode 0, Depth = mode 1 (C2 at its 3.68 mm focal-length limit), Auto resolution = a separate flag. Auto resolution picked 150 / 90 / 70 / 50 pA at 20 / 10 / 5 / 2 kV.
  • No hysteresis: every state repeated to within a few counts; magnification never touches the lenses.

10Other interfaces worth knowing

  • VP / "Orsay" controller (hpapp.exe, 1998): PC COM2:9600,n,8,1. Commands seen: RE 0 reset, ST 1,%d to ST 5,5 timeouts, TO %d, HP %d,%d,%d pressure target, MC 100,900. It has its own state names (AT_AIR_HP, PUMPING_LP, GOING_TO_HP…), a debug log option, and OrsayBoardTimeout=300 in C:\WINDOWS\LEO.INI.
  • Licence dongle: DESkey DK2 on the parallel port (DK2WN95.386, DK2WIN32.DLL imported directly by leoserv.exe). M600 stores the serial number and licence bits on it ("Re-write Licences to Dongle"). M600 also refers to a backup file C:\leo\data.dgl, which is not on this image. HASP and Hardlock drivers are also installed, probably for third-party software.
  • RemCon32: LEO's documented RS-232 remote-control protocol (remcon32.exe, REMCON32.HLP). It drives the whole stack from outside and is a cheap way to script repeatable actions while capturing the fiber links.
  • DDE / LEOAPI.OCX: the same parameter set is reachable by DDE and by an ActiveX control used by EDS vendors (Oxford ISIS, Link, iXRF).
  • Calibration data: C:\LEO\*.VAC (vacuum NVRAM copies), gamma2.dat and loc*/loi*.dat (HRRU photo tables), L500.INI (filament limits, VP target 9, VP limit 274), and the Access database LEO_USER.MDB (users, apertures, column calibration). A replacement system needs these values even if none of the code is reused.

12Replacement paths

The board does three separate jobs: serial links to slow subsystems, real-time scan generation with image acquisition, and display. These can be replaced at different speeds. The recommended order goes from cheapest-to-verify to hardest.

Stage 2 · capture and confirm · low risk

A. Instrument the fiber links before changing anything

  • Identify the fiber connectors and transceivers on the board (likely HP/Agilent HFBR "Versatile Link" plastic fiber or ST glass). Build passive taps or receive-only adapters to TTL, then into a USB logic analyser or USB-UART adapters.
  • Confirm 9600 8N1 on the two UART links and log full sessions: power-up, stage init, pump/vent, EHT on, filament ramp. Correlate the log with the .S?/.V?/EHT character tables above.
  • For each remaining fiber, measure the bit rate and framing. Expect higher-speed synchronous or Manchester data for scan and video.
  • Use RemCon32 or macros to repeat single actions, and the EHT direct-command service panel to probe the EHT unit by hand.
  • Disassemble the GSP modules with MAME's unidasm (it supports tms34010 and tms34020) or a Ghidra TMS340 processor module. With the symbol tables applied, _send_stage_command, _decode_vac_status and _interpret_cmd_response will give exact argument formats.
  • Image the drive and dump the board's EPROM and LCA bitstream before any hardware change. Read and save the DESkey dongle contents.
Stage 3 · modern PC, existing board · medium risk

B. Keep the ISA board, replace the PC and software

The interface is simple: two page registers and a 32 KB window. A modern host can drive the board through an industrial PC with an ISA slot, or through an LPC/PCIe-to-ISA bridge.

  • Write a small user-space driver for 0xA300/0xA301 and the D0000 window. Reproduce the boot steps (LCA load, halt, EPROM off, load TIGAGM.OUT).
  • Write a COFF loader for the existing g*.rlm / .440 modules, or call into them through TIGAGM. Then invoke the documented .TIGAEXT functions by index. This reuses the proven real-time firmware and moves only the UI.
  • Fallback during development: run the original Win98 image on the new ISA-capable PC as a known-good reference.
Stage 4 · new hardware · higher risk

C. Replace the board with a new controller

  • Slow links first. The EHT and Stage/Vac links are 9600-baud ASCII. A microcontroller or a PC with two fiber-to-UART adapters can take them over early, gated by a supervisor that keeps the original interlocks (vacuum state machine, beam-off-before-vent, stage touch alarm).
  • Scan and acquisition. An FPGA board (for example a Zynq or a small FPGA with a USB3 or Ethernet bridge) generates the raster, drives the scan/EO link in whatever format Stage 2 finds, and digitises or receives detector video. The DPRAM variable map defines the feature set to match: 16 scan origins and amplitudes, dual-mag, stereo, line and frame integration, freeze, spot mode.
  • Display and UI on a normal PC. With the frame store in the FPGA or on the host, overlay mixing is no longer needed and the VGA pass-through disappears.
  • Calibration carry-over. Port the lens and mag calibration math in M200.DLL/g200.440 (C1/C2/C3 cal and rem values, mag tables, scan orthogonality) and the stored values from LEO_USER.MDB and config.LEO.
Recommendation (12 Nov). Do path A now. It is cheap, it tells you whether the EHT timeouts are a link problem, and it decides whether path B is worth doing. If the scan and video fibers turn out to be simple, go straight from A to C and skip the bridge work in B.
What happened (to 15 Nov).
  • Path A is done. All links were captured and specified, and the scan fibers turned out to be simple serial frames plus two gates. So the project went straight to path C, without an FPGA scan engine.
  • Control box. A Teensy 4.0 board (hardware/leo_control_box, PCB at the fab; firmware in firmware/leo_control) drives the EHT, stage / vacuum and VP links and the four EO fibers. It owns the machine state and every safety rule: filament off and cooled before any pressure change, ramps, fault handling, the VP watchdog. It computes the scan-coil weights and the lenses (§9).
  • Imaging. The Open Beam Interface (Glasgow) images through the EO board's external scan input.
  • User interface. A browser page (webui/) talks to the box over Web Serial and to OBI through a local bridge. It replaces LEO-32: focus = WD, probe current, Optibeam mode and aperture, magnification, stigmator pad, beam and vacuum control, 16-bit TIFF capture.
