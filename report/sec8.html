8Scan generator path: DSP, raster engine and the four fibers

This section goes deeper than the first pass. The DSP program image (DPRAM.IMG) and the GSP's DSP driver (g900.rlm) were both decoded far enough to follow a scan setting from the user interface down to the registers on the far end of the link. The picture: the PC never streams X/Y samples. The DSP loads start, step, count and flyback values into a hardware raster generator, sets a pixel clock, and then updates registers only per line or per user action.

The DSP is an Analog Devices ADSP-21xx

DPRAM.IMG stores 24-bit words as three bytes plus an FF pad, which is the GSP's 32-bit view of a 24-bit program RAM. The words decode cleanly as ADSP-2100-family code: interrupt vectors every 4 words, RTI=0A001F, RTS=0A000F, DO…UNTIL loops, DIVQ division. The control-register writes match an ADSP-2101/2105-class part: system and wait-state registers at DM 0x3FFE/F, the timer at 0x3FFB–D, SPORT1 at 0x3FF1/2, and internal data RAM at 0x3800. Program words 0x000–0x3F7 are a small resident monitor (command loop and code download). The scan firmware itself lives at PM 0x2000–0x2C99 (about 3,200 instructions).

GSP view of the same RAM

From the TMS34020, the dual-port RAM sits at bit address 0x60480000 + (offset << 5), one byte per 32-bit slot (_cp_write_dpram: SLL 5, then AND 0xFF on read). The GSP writes parameters, writes a command byte to offset 0x400, and polls until the DSP clears it (_WaitForDSPCommand). The DSP's main loop reads DSP 0x0800, indexes the jump table at 0x393F, runs the handler, clears the command, sets STATUS (0x401) and raises a GSP interrupt (DSP 0x005F ← GSPINTEN).

The program image is downloaded with DSP command 0x01 (copy a 256-word block from the transfer buffer into program RAM) before SEM_INIT.DAT runs.

The remote register bus

Every write the DSP makes to the scan hardware, and every lens or stigmator value the GSP sends, goes through one routine at PM 0x2457:

; DSP PM 0x2457 — write AX0 to remote register (I4 − 0x3400) on target "EO"
AF = 0x0040                    ; target code: 0x40 = EO board  (entry 0x247F uses 0x20 = HRRU)
wait: AR = DM(0x37FF) AND 0x0004; IF NE JUMP wait   ; link busy?
AR = (shadow AND 0xFF9F) OR AF ; DM(0x0040) = AR     ; select target in link-control reg
DM(I4) = AX0                   ; I4 = 0x3400 + register → link sends (address, 16-bit data)
; PM 0x2468 (read): select target, dummy read DM(I4), wait busy, read DM(I4) again → value
  • Address space: 10 bits (0x000–0x3FE) per target, 16-bit data. Targets are selected by bits 5–6 of IP-board register 0x40: 0x40 = EO board, 0x20 = HRRU (the photo recording unit).
  • GSP access: _set_eo_register fills TRANSSTARTADD (0x405/6) with the register number, TRANSNUMBER (0x407/8) with a count, data in the transfer buffer, and TRANSCTRL (0x409) = 0x40, then issues DSP command 0x04. Lens, stigmator and condenser code in g200.440 (_write_EO_value, _gsp_set_C3_current, _gsp_set_condenser_lens_current …) all end up here. So the same link carries both lens/stig set-points and raster-generator settings.
  • Traffic: bursts only. There is one write per register, gated by a busy flag. The DSP writes a handful of registers per scan-rate or format change and a few per line (Y position from the line interrupt). This is the low-bandwidth "EO command" channel you expected.
  • Readback exists. The firmware reads remote registers 0x4B, 0x14 and 0x30 and the EO board version, waiting on the busy flag for the reply. If all four fibers really run IP-board → scan generator, these reads must be served from a copy on the IP board. Otherwise there is a return fiber or a copper path. Checking transmitter vs receiver parts on the board settles this (HFBR-15xx are transmitters, HFBR-25xx receivers).

Remote register map (EO target)

The registers fall into five blocks: four identical 32-register "deflection channels" and a common block. The HRRU target uses the same layout for its X/Y channels, which suggests one raster-generator design (probably an LCA or ASIC) reused in both units. Meanings below come from how the firmware computes each value. Treat them as working names until confirmed on a capture.

How a raster is defined (DSP command 0x07)

Scan coordinates are 16-bit offset-binary DAC codes centred on 0x7FFF. The full field is MAXPIXELS × MAXLINES (1024 × 0x303 by default), and a sub-raster (reduced raster, split screen, zoom) is a window inside it. The handler computes:

xstep = 0x7FFF / MAXPIXELS                      ; 31 for 1024 (DIVQ routine at PM 0x2447)
reg 0x40  X start      = 0x7FFF − xstep·MAXPIXELS + 2·xstep·STARTPIXEL   ; 0x03FF for a full raster
reg 0x42  X pixel step = 2·xstep                         ; 62 codes per pixel → 0x03FF … 0xF7FF
reg 0x48  pixels/line  = NUMPIXELS
reg 0x49  blank pixels = BLANKPIXELS, or (0x110|0x120 + k)·f(rate) if 0
reg 0x41  flyback step = 2·(xstep·NUMPIXELS / blank)    ; ramp returns during horizontal blanking

ystep = 0x7FFF / MAXLINES
reg 0x60  Y start  = 0x7FFF − ystep·MAXLINES + 2·ystep·STARTLINE
reg 0x62  Y step   = 2·ystep        reg 0x68 lines = NUMLINES     reg 0x69 = BLANKLINES
reg 0x61  Y flyback step = 2·(ystep·NUMLINES / BLANKLINES)
reg 0x4B  read → write 0 (stop) → reprogram → restore old value (restart)

; spot mode (cmd 0x19) uses the same scale: reg 0x54 = 0x7FFF − xstep·MAXPIXELS + 2·xstep·SPOTX, reg 0x74 likewise for Y

This is a classic digital differential (DDA) raster: each axis has a start code, a per-step increment, a count, and a flyback increment spread over the blanking interval. That pattern only makes sense if an accumulator on the far side adds the step on every pixel clock, with the result driving the scan DACs. Magnification is applied elsewhere, by analogue gain on the scan-coil drivers (mag-range register 0x4D, SCANAMP, FASTLINEAMP/SLOWLINEAMP in DPRAM). Rotation, dual-mag and post-rotation offsets are loaded as coefficient sets into the 0x14/0x15, 0x32/0x33 and 0x71–0x76 registers (commands 0x1A, 0x21, 0x2B).

How the pixel clock is made (DSP command 0x06)

  • SCANRATE (DPRAM 0x40A, 0–15, default 5) is the dwell-time index; M200 exposes 16 rates (DOCOMMANDSCANRATE0…15).
  • For rate ≥ 3 the DSP sets SPORT1 SCLKDIV = 2(rate−3) − 1 with internal SCLK enabled (control 0x6002). The SCLK1 pin then runs at CLKOUT / 2(rate−2), halving at each step. Rates 0–2 use a fixed divider plus a 2-bit local divider in IP-board register 0x58.
  • For rate > 9 the DSP also programs remote register 0x4A = 2(rate−9) − 1 and switches 0x4B from 0x8402 to 0x8422. In other words, a further divider on the far-end board is enabled. A prescaler at the far end only makes sense if that board receives a clock to divide.
  • Rates above DPRAM SLOWLINERATE (6) and DIGILINERATE (8) set mode bits 0x08/0x18 in register 0x4D (slow-line and digital-line modes) and change register 0x4C between 4 and 8.
  • The DSP takes a per-line interrupt (IRQ1 → PM 0x0200) that counts lines, switches between rasters (split/quad/dual-mag), handles end-of-frame, and writes per-line values such as Y position 0x74. The timer interrupt (PM 0x2000) handles slower periodic work (stereo, frame averaging).

The DSP crystal frequency isn't in the software, so absolute dwell times need a scope. The ratios are fixed: each scan-rate step should halve the frequency on the clock fiber.

Alternative to rule out. The raster engine could sit on the IP board, with the fibers carrying serialised 16-bit X and Y codes at the pixel rate. Two things argue against this: the lens set-points share the same register space, and the slow-rate prescaler (0x4A) is a register on the EO target. It is still cheap to check. If a fiber shows dense data at every pixel clock whose content ramps along the line, the DDA is local and that fiber carries DAC samples.
